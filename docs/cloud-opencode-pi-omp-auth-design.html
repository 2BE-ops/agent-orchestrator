API-key provisioning for OpenCode, Pi, and OMP

How AO Cloud can launch any of these three harnesses with a preconfigured provider while the user supplies only an API key—without putting the secret in the pod definition, image, configuration file, or command arguments.

Status: Proposed Runtime: Debian Linux Example provider: Z.AI Updated: 4 September 2026
Decision Flow Catalog Harnesses Z.AI variants Security Tests Sources

Decision

AO owns the harness image and provider recipe. The user supplies only the provider choice, model choice, and write-only API key.

Use one immutable image per harness—not one image for every provider. A server-side provider catalog adds the non-secret configuration and maps the submitted credential to the environment variable expected by that harness.

Hard rule: never place the API-key value in a Kubernetes Pod manifest, NodeOps template, image layer, ConfigMap, command argument, generated provider file, label, response, audit event, or log.

Creation and launch flow

1. SelectUser chooses OpenCode, Pi, or OMP plus an approved provider profile and model.
2. SubmitAO receives the API key in a write-only field over its authenticated API.
3. StartAO creates the sandbox from the pinned harness image without the secret.
4. RedeemThe signed worker retrieves the pending key once using its session identity.
5. LaunchThe worker applies the provider recipe and starts only the selected harness.
6. VerifyA bounded provider/model probe passes before the first user turn starts.

Single client-facing request

{
  "harness": "pi",
  "providerProfile": "zai-global",
  "model": "glm-4.7",
  "credential": {
    "type": "api_key",
    "value": "<write-only secret>"
  }
}

The response contains a session identifier and authentication state, but never returns credential.value. The request body must be excluded from access logs, traces, error reports, and analytics.

Image and provider catalog

Harness images

  • ao-opencode:<pinned-version>
  • ao-pi:<pinned-version>
  • ao-omp:<pinned-version>

Images contain the harness, runtime dependencies, AO worker, and non-secret defaults. They contain no user credential.

Provider recipe

  • Harness-local provider ID
  • Allowed model IDs
  • Native secret environment name
  • Optional non-secret config overlay
  • Launch and validation commands
  • Required endpoint/product variant
type ProviderRecipe struct {
    ID                string   // AO-owned semantic profile
    HarnessID         string   // opencode | pi | omp
    HarnessProviderID string   // provider ID used by this harness
    ImageDigest       string
    HarnessVersion    string
    AllowedModels     []string
    SecretEnvName     string   // ZAI_API_KEY
    ConfigFiles       []File   // non-secret content only
    LaunchArgs        []string // never contains the API key
    ProbeArgs         []string
}
Catalog boundary: clients cannot submit arbitrary environment names, base URLs, executable commands, or provider configuration. They select a reviewed recipe already present in the AO catalog.

Harness-specific implementation

OpenCode

Template behavior

  • Install a pinned OpenCode release.
  • Use an isolated XDG config/data directory.
  • Bake or mount a non-secret opencode.json.
  • Reference ZAI_API_KEY through OpenCode's environment interpolation.
  • Select the configured provider/model without running interactive /connect.
Pi

Template behavior

  • Install pinned Pi and compatible pi-acp releases.
  • Set PI_CODING_AGENT_DIR to an empty session-owned directory.
  • Inject Pi's documented ZAI_API_KEY.
  • Select provider/model through CLI flags or the ACP model option.
  • Do not use --api-key; it would expose the secret as a process argument.
OMP

Template behavior

  • Install a pinned OMP release.
  • Set PI_CODING_AGENT_DIR to an empty session-owned OMP directory.
  • Inject OMP's documented ZAI_API_KEY.
  • Select a qualified provider/model.
  • Do not use --api-key; isolate the directory so stored credentials cannot override the runtime key.

Secret delivery and hardening

Initial implementation

  1. Receive the key in a write-only AO API field.
  2. Keep it in a short-lived encrypted pending-secret record.
  3. Start the sandbox without the key.
  4. Allow only the assigned worker epoch to redeem it once.
  5. Inject the native variable only into the harness child process.
  6. Invalidate the pending record and destroy all runtime material at shutdown.

Hardened implementation

  1. Keep the real key in an AO-owned loopback credential proxy.
  2. Point the harness provider recipe at the proxy using custom baseURL configuration.
  3. Give the harness only a sandbox-local placeholder token.
  4. Have the proxy add the real upstream authorization header.
  5. Restrict proxy destinations to the recipe's approved provider host.
Why the proxy matters: OpenCode, Pi, and OMP can execute shell tools. A process can usually read its own environment, so direct environment injection prevents infrastructure leakage but does not hide the key from the harness itself. The loopback proxy keeps the raw upstream key outside the agent process.

Required controls

  • Never log request bodies for credential-bearing endpoints.
  • Bind redemption to organization, user, session, worker epoch, harness, and provider recipe.
  • Use a short expiry and strict single redemption.
  • Do not inherit the control-plane environment into the sandbox or harness.
  • Start Pi and OMP with empty isolated agent directories to avoid higher-priority stored credentials.
  • Redact secret-looking values from worker diagnostics, traces, crash reports, and terminal capture.

Acceptance tests

  • Each clean Debian image reports its exact pinned harness version.
  • OpenCode, Pi, and OMP each complete a real bounded Z.AI provider/model probe.
  • Changing only the submitted key requires no image rebuild.
  • The credential cannot be found in the pod definition, template, image history, config files, process arguments, API responses, logs, traces, or audit rows.
  • A pending credential can be redeemed once by the assigned worker and no other worker.
  • An expired, revoked, wrong-product, or wrong-provider key returns login_required with a redacted diagnostic.
  • A stale Pi auth.json or OMP agent.db from another session is never visible to a new sandbox.
  • An unsupported harness/provider/model combination is rejected before sandbox creation.
  • Hardened proxy mode refuses unapproved upstream hosts and never returns the upstream key.

Recommended first slice: implement the direct-environment path for one verified Z.AI product across OpenCode, Pi, and OMP, with isolated state and redaction tests. Add the loopback credential proxy before treating arbitrary repositories or unattended workloads as fully hardened.
