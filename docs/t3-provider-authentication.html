Start with the authentication boundaries

Environment authentication

Determines whether a web, desktop, or mobile client may connect to a T3 environment and invoke HTTP/WebSocket methods.

Pairing credentials, bearer/DPoP sessions, scopes, WebSocket tickets.

Agent/provider authentication

Determines whether a configured Codex, Claude, Cursor, Grok, OpenCode, or Antigravity instance appears able to run.

This is the system described by the rest of this document.

Source-control authentication

Separately checks GitHub, GitLab, Azure DevOps, or Bitbucket credentials used for clone and pull-request operations.

A working Codex login does not imply that gh is authenticated.

The provider state model

T3 does not reduce provider readiness to one boolean. Each instance exposes four independent axes:

enabledUser configuration. Disabled instances cannot start sessions.
installedWhether T3 located and executed the CLI/runtime.
statusOverall health: ready, warning, error, or disabled.
auth.statusEvidence about credentials: authenticated, unauthenticated, or unknown.
authenticated

T3 obtained affirmative evidence of an account, usable credential method, or connected upstream provider.

unauthenticated

The provider produced a definitive logged-out or login-required signal. T3 can show a specific recovery action.

unknown

The probe was inconclusive, failed, timed out, has not run, or cannot validate account access without a real session.

unknown is not “logged out.” A provider may legitimately be status: "ready" while its auth status is unknown. The real provider launch is allowed to make the final determination.

End-to-end lifecycle

1. ConfigureResolve an instance, driver, binary, home, and environment.
2. HydrateLoad the last correlated snapshot from the per-instance cache.
3. ProbeRun the provider-specific, bounded health/auth check.
4. NormalizeProduce installed, version, status, auth, models, and message.
5. MergeReconcile cached catalogs and Antigravity account evidence.
6. PublishPersist the machine snapshot and stream the provider list to clients.
7. RunThe adapter starts the actual provider and remains the final authority.

Provider snapshots can also change because of usage updates, version enrichment, workspace skill discovery, or session callbacks. Those emissions do not necessarily re-run authentication.

Codex

T3 starts a scoped codex app-server, completes its initialize handshake, and calls account/read. If the response says OpenAI auth is required, the snapshot becomes an error with the instruction to run codex login.

When the account response is not definitively logged out, the same process also retrieves models, skills, and account rate limits. Rate-limit failure is treated as optional enrichment and does not discard the account result.

Timeout
10 seconds for the overall provider probe; 3 seconds for the optional rate-limit read.
Metadata
Account type, plan label, email, models, skills, and usage limits.
Isolation
Per-instance process environment and CODEX_HOME/shadow-home layout.
Login
codex login outside T3.
Claude

T3 first checks the executable with claude --version. It then creates a Claude Agent SDK query whose asynchronous prompt never yields a user message. The child completes local initialization and returns account data, but no prompt reaches Anthropic.

The probe disables hooks, filesystem and Claude.ai MCP connections, tools, and IDE discovery. Successful initialization is treated as authenticated; failure to obtain the initialization result becomes unknown rather than definitively logged out.

Timeout
4 seconds for version; 25 seconds for SDK initialization.
Cache
Capabilities cached for five minutes per binary/home/workspace key.
Metadata
Email, subscription type, API-key source, Bedrock backend, slash commands, and usage.
Login
claude auth login outside T3.
Cursor

The current implementation asks agent about --format json for version, email, and subscription tier in one call. If that CLI version does not support JSON formatting, T3 retries with plain agent about and parses labeled fields.

Only a definite missing/null email or login-required phrase becomes unauthenticated. A clean result with no email remains ready with unknown auth. ACP model discovery runs afterward unless logout was confirmed.

Timeout
8 seconds for agent about.
Metadata
Email, subscription tier, CLI version, ACP-discovered models.
Compatibility
Old CLIs without the required model-picker protocol become an actionable provider error.
Login
agent login outside T3.
Grok

T3 checks grok --version, then parses grok models. The command may exit zero while logged out, so stdout/stderr text—not the exit code alone—determines login state. The environment variable recognized by this implementation is XAI_API_KEY.

Model discovery also uses ACP initialize. This deliberately avoids authenticate and session/new, preventing a health check from opening a browser or starting workspace MCP servers.

Timeout
4 seconds for version, 10 seconds for auth listing, 8 seconds for ACP initialization.
Auth types
api_key or cached_token.
Failure
Definitive logout is an error; failed ACP metadata discovery is only a warning.
Login
grok login outside T3.
OpenCode

OpenCode is a meta-provider. T3 connects to a locally owned or external OpenCode server and loads its inventory. Authentication means that the inventory reports at least one connected upstream provider—not that OpenCode has one global account.

Zero connections produce a warning and unknown auth, never unauthenticated. Local OpenCode must be at least version 1.14.19. External server passwords authenticate T3 to that server and are separate from upstream model-provider credentials.

Periodic
Disabled. Use explicit provider/model refresh or instance reconstruction.
Metadata
Connected upstream count, models, skills, commands, and server version.
Failure
Connection, version, or inventory failures produce error + unknown auth.
Login
Managed using OpenCode's own provider configuration.
Antigravity

The passive check performs ACP initialize only. It can prove installation and health, but not account access. Account authentication and model discovery happen through an explicit setup/catalog session or a real provider session.

Each instance receives a private credential profile. T3 forces file credential storage and removes ambient Google credential variables so one instance cannot silently adopt another account. Installed runtime releases may still be shared.

Health timeout
90 seconds.
Methods
Personal OAuth, Enterprise OAuth, Gemini API key, and Agent Platform/Vertex AI.
Positive proof
An authenticated session starts and returns account-specific models.
Negative proof
Native auth-required notification or explicit sign-out.

Interactive authentication: Antigravity

Only a provider instance exposing a ProviderAuthController can use T3's centralized sign-in RPCs. In the current built-in set, that is Antigravity.

StartT3 creates a random flow ID, binds it to the initiating environment-auth session, and sets a five-minute expiry.
Quiesce the instanceActive sessions and owned helper processes for that provider instance are stopped before authentication proceeds.
Obtain authorizationThe ACP runtime requests an authorization URL. Browser-based flows enter waiting; API-key methods check configured credentials directly.
Return the callbackFor a remote browser, the initiating client pastes the complete loopback return URL. T3 validates it against the owned pending flow and forwards it.
VerifyThe native process completes token exchange and starts a session. Callback delivery alone is not considered proof.
Publish account stateSuccessful session data marks the provider authenticated and publishes its account-specific models and commands.
Other connected clients can learn that sign-in is in progress, but the controller hides the flow ID, authorization URL, and expiry from every client except the initiating T3 auth session.

Cache, refresh, and stale-state handling

Per-instance cache

Snapshots are stored as <instanceId>.json. Both instance ID and driver kind must match before cached data is accepted.

The cache stores status metadata, not provider access tokens.

Preservation rules

A transient failure should not erase a previously useful catalog. Custom models, however, come from current settings and are never resurrected from stale cache entries.

Antigravity carry-forward

A prior authenticated account can survive a new unknown health result when the sign-in method is unchanged and no authoritative sign-out occurred.

A manual server.refreshProviders RPC can refresh all instances, one instance, or workspace-specific metadata. An untargeted refresh also refreshes configured usage-limit sources. Settings and onboarding expose this operation; closing an onboarding login terminal triggers it so newly changed CLI credentials appear promptly.

How T3 differs from Agent Orchestrator

The systems share one important rule: a passive check is evidence, while the native provider process remains the final authority. Their center of gravity is different. T3 builds a rich, persistent provider catalog for six deeply integrated provider drivers. AO builds a normalized, request-driven readiness service across a much broader set of heterogeneous harnesses, then keeps login commands and provider credentials behind separate boundaries.

AO comparison reviewed at local commit 7b8ee8db080b, 12 September 2026.

T3’s unit: provider instance

Each instance has its own driver settings, environment, snapshot, adapter, and optional auth controller. Multiple instances of one provider are a normal part of the model.

AO’s unit: harness readiness

The generic coordinator keeps one installation/authentication observation per harness ID. Its concern is whether a requested launch can proceed safely now.

The exceptions are different

T3’s deep interactive exception is Antigravity. AO’s deep account-management exception is Codex; other AO providers use reviewed native login/setup plans.

Generic readiness intentionally omits account identity. T3 is richer for account display; AO is richer for operational diagnosis and safe API consumption.
Refresh policy Managed provider streams run initial, settings-driven, manual, and normally five-minute power-aware refreshes. OpenCode opts out of periodic refresh. Demand-driven ensure: five-minute display TTL and thirty-second launch TTL, with a bounded startup warm-up, four workers, single-flight sharing, and retry backoff. AO asks “is this fresh enough for this purpose?”; T3 continuously maintains a provider-facing catalog.
Failed checks Return unknown and often retain useful prior provider/model metadata through merge rules. Keep the last successful state and checkedAt, record the failed attempt and reason, mark it stale, and retry after 15 seconds, 1 minute, then 5 minutes. Neither converts uncertainty into a false logout. AO exposes the distinction between old evidence and a failed new attempt more explicitly.
Persistence Correlated provider snapshots are persisted per instance and hydrated at boot for immediate UI state. Generic readiness lives in daemon memory and starts unknown/stale after restart. Codex account descriptors, opaque credential homes, and the active-account pointer are a separate persistent subsystem. T3 can render the last provider catalog immediately; AO prefers a new warm-up for generic readiness.
Interactive login The centralized auth service works only when a provider supplies a controller; among built-ins, only Antigravity does. Other providers tell the user which native CLI command to run. A code-reviewed allowlist currently exposes 27 native login/setup targets. The client chooses only an agent ID; the daemon resolves the binary and opens a trusted command terminal or documentation. AO offers broader in-app entry into vendor-owned login flows without accepting arbitrary commands or credentials from clients.
Deep account ownership Antigravity owns an OAuth/credential-method state machine, private per-instance profile, callback forwarding, verification, and logout. Codex owns managed account slots, native-login terminals, structured verification, account switching, logout/reauthentication, capacity, and usage. It copies opaque credential material but does not parse or expose it. Both have one provider-specific subsystem that is much deeper than their generic login path, but for different providers.
Multiple identities Generic: multiple configured instances of any driver can use isolated homes/environments. Generic readiness is keyed by harness. Multiple managed identities are currently a dedicated Codex feature rather than a universal provider-instance abstraction. T3’s multi-account shape is more uniform; AO’s is deliberately provider-specific.
Launch enforcement The generic session service requires an existing enabled instance but does not universally require a cached authenticated verdict; provider startup is authoritative. Definitely missing installation blocks session creation. Generic auth warnings may continue to native launch; Chat driver probes and agent switching reject definitive unauthorized results. Fresh structured Codex logout is blocked before spawn. AO has more explicit launch-purpose checks, but its policy is intentionally layered rather than one global “auth must be green” gate.
Catalog coupling Auth affects provider health, model retention, pickers, load balancing, and advisories inside one snapshot pipeline. Readiness is separate from model catalogs and from auth-launch plans; frontend state is a cached projection whose freshness remains daemon-owned. AO has cleaner separation of concerns; T3 has a more unified provider presentation model.

The same six providers, checked differently

ProviderT3 checkAO checkMost important difference
Codex App-server account/read; returns account type, plan, email, models, skills, and limits. The structured Codex account manager also uses app-server account/read when available and verifies the active managed account using display/launch freshness rules. The adapter-level fallback runs codex login status. AO goes beyond probing: it can add, retain, reauthenticate, switch, sign out, and inspect capacity for multiple managed Codex accounts. T3’s generic Codex provider does not expose its centralized in-app auth controller.
Claude Starts a deliberately promptless Agent SDK initialization and reads returned account/capability metadata. First recognizes approved environment variables and safe fields in local Claude configuration, then falls back to claude auth status JSON. T3 asks the SDK/runtime for richer live initialization evidence; AO prefers cheaper local evidence and the CLI’s explicit status command.
Cursor Parses agent about --format json or text; email and subscription data drive the verdict. Accepts CURSOR_API_KEY, otherwise runs cursor-agent status and classifies known status text. T3 collects account metadata; AO asks only for a normalized readiness verdict.
Grok Accepts XAI_API_KEY or parses grok models, including explicit logged-out text. Checks XAI_API_KEY, documented secrets or environment references in config.toml, and tokens in auth.json. T3 can derive a definitive negative from CLI output. AO’s local-file probe mostly proves presence; absent evidence remains unknown instead of unauthorized.
OpenCode Uses the live server inventory and treats one or more connected upstream providers as authenticated. Checks supported API-key variables, auth.json, recognized read-only database account state, then opencode auth list. No credential remains unknown because public free models may still work. T3’s verdict is server/catalog-based; AO combines local configuration evidence and CLI fallback while preserving “no credential” as usable uncertainty.
Antigravity / Agy Passive ACP initialization proves health only. T3 later gets auth evidence from sessions and owns the full provider auth controller. Because Agy has no documented non-interactive status command, an installed binary is reported authorized and the real launch remains authoritative. The reviewed login plan starts agy for its native first-run browser flow. T3 models and manages this authentication deeply; AO deliberately uses optimistic readiness plus native runtime validation.

AO is stronger at orchestration readiness

Purpose-specific freshness, single-flight checks, bounded concurrency, retry scheduling, stable reasons, and an explicit derived readiness state scale well across many harnesses.

T3 is stronger at generic provider identity

Per-instance isolation, persisted snapshots, account labels, emails, subscription types, and model/catalog merging are consistently available across its smaller provider set.

The main AO caveat

“Authorized” can mean different strengths of evidence. Codex may be freshly verified, while Agy currently means only “installed; let launch decide.” Consumers must keep the reason and freshness—not just the state.

Important conclusions and corrections

  1. The snapshot is evidence, not a security boundary. Credentials can change between probes, and the runtime remains authoritative.
  2. Not every snapshot update checks auth. Usage, version enrichment, workspace metadata, and session callbacks also publish snapshots.
  3. Cursor auth currently comes from agent about. ACP is used afterward for model discovery.
  4. Grok's API-key environment variable is XAI_API_KEY.
  5. Claude's current verdict comes from SDK initialization. It does not produce a normal definitive unauthenticated branch in the snapshot probe.
  6. OpenCode does not periodically poll. Its inventory is intentionally refreshed through explicit workflows.
  7. Antigravity is not only browser OAuth. The controller also handles non-browser credential methods, private per-instance profiles, process admission, and sign-out.
  8. Both Antigravity sign-in and sign-out stop active instance sessions. This prevents processes from retaining or racing old credentials.
  9. AO is not a direct clone of this design. It separates readiness, model discovery, and trusted login launch; only its Codex subsystem approaches T3’s deep provider-specific account ownership.
