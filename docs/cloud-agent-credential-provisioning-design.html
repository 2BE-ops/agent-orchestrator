Technical design

Credential provisioning for AO Cloud agent sandboxes

A provider-aware design for launching an agent in an ephemeral Debian Linux sandbox. The selected template contains the agent and non-secret provider configuration; the user supplies only the API key at creation time.

Status: Proposed Runtime: Debian Linux Worker UID: 10001 Updated: 4 September 2026
Decision Baseline Architecture Three harnesses Contract Harness matrix Security Rollout Tests Sources

Decision

AO Cloud will use harness + provider templates. The template contains all non-secret configuration; the create request supplies only the API key.

For example, the opencode-zai, pi-zai, and omp-zai templates each install a pinned harness version and select the Z.AI provider and model. AO delivers the submitted key after the sandbox starts and exposes ZAI_API_KEY only to the selected harness process.

Hard rule: the API key value must not appear in a Kubernetes Pod manifest, NodeOps template, container image, command argument, label, log, or generated config file. “Pass the API while creating” means a write-only secret field over the authenticated AO API, followed by one-time delivery to the worker.

End-to-end architecture

1. SelectUser selects the harness, provider, and model; for example OpenCode + Z.AI + GLM.
2. SubmitUser sends the API key in a write-only field over the authenticated AO create-session API.
3. ProvisionThe reconciler creates a Debian sandbox from the matching immutable harness + provider template.
4. DeliverAfter boot, the authenticated worker redeems the pending key exactly once over the control channel.
5. InjectThe worker adds the key to the child process environment named by the template.
6. VerifyA bounded provider/model probe must pass before the first real turn starts.
7. DestroyStopping the sandbox removes the process and all transient secret material.

Control-plane responsibilities

  • Authorize organization, user, harness, provider, and model access.
  • Validate the selected combination against the template catalog.
  • Hold the submitted key only in an encrypted, short-lived pending-secret record.
  • Issue a single-use secret lease scoped to one session and worker epoch.
  • Audit creation, delivery, revocation, and failed validation without secret content.

Worker responsibilities

  • Prove its session identity before requesting the pending API key.
  • Inject only the template’s allowlisted environment variable into the agent child process.
  • Run the harness under UID 10001.
  • Never write the API key to shell profiles, project files, or the agent’s persistent home.
  • Return status codes and redacted diagnostics, never credential bytes.

Concrete examples: Z.AI on three harnesses

Template: opencode-zai

  • Debian Linux base with a pinned OpenCode build.
  • Non-root worker and isolated writable OpenCode data directory.
  • Provider fixed to zai for a standard Z.AI API key. A GLM Coding Plan account uses a separate zai-coding-plan template.
  • Default model fixed to a model supported by the pinned build.
  • Config references {env:ZAI_API_KEY}; it never contains the key value.

Template: pi-zai

  • Installs a pinned @earendil-works/pi-coding-agent and, for AO Chat, the compatible pi-acp.
  • Sets PI_CODING_AGENT_DIR to an empty session-owned directory so no stored auth.json overrides the supplied key.
  • Injects ZAI_API_KEY and selects zai/glm-4.7.
  • Does not use --api-key, because secrets must not appear in process arguments.

Template: omp-zai

  • Installs a pinned omp build.
  • Sets PI_CODING_AGENT_DIR to an empty session-owned OMP directory so agent.db, .env, or models.yml cannot override the runtime key.
  • Injects ZAI_API_KEY and selects zai/glm-4.7.
  • Avoids OMP's higher-priority --api-key option because command arguments can be inspected.

One create-session shape for all three

{
  "harness": "opencode",
  "providerTemplate": "zai",
  "model": "glm-4.7",
  "apiKey": "<write-only secret>"
}

For Pi or OMP, only harness changes. The response and every later read omit apiKey. A retry uses an idempotency key; AO must not echo or log the request body.

Non-secret OpenCode config baked into the template

{
  "$schema": "https://opencode.ai/config.json",
  "model": "zai/glm-4.7",
  "provider": {
    "zai": {
      "options": {
        "apiKey": "{env:ZAI_API_KEY}"
      }
    }
  }
}
Runtime launch: the worker uses a process API with an environment map containing ZAI_API_KEY=<secret>. OpenCode reads it through the config placeholder; Pi and OMP read it through their built-in Z.AI provider mapping. The key never becomes a command argument or shell command.
Trust boundary: a harness with shell tools may be able to inspect its own environment. Direct environment injection is the simplest officially supported implementation, but the hardened mode keeps the real key in an AO-owned loopback credential proxy. The provider recipe points the harness at that proxy using its documented custom baseURL support; the proxy adds the real upstream authorization header. The harness receives only a sandbox-local placeholder token.

Harness + provider template contract

type ProviderTemplate struct {
    ID                 string   // "opencode-zai"
    HarnessID          string   // "opencode"
    ProviderID         string   // "zai"
    RootFS             string   // immutable NodeOps template digest
    HarnessVersion     string
    ConfigFiles        []File   // non-secret files only
    SecretEnvName      string   // "ZAI_API_KEY"
    AllowedModels      []string
    StatusCommand      []string
    SecretPersistence string   // "ephemeral" by default
}
Catalog rule: clients send a template ID and an API key. They cannot send arbitrary environment variable names, file paths, install commands, base URLs, or executable configuration. Those are controlled by the reviewed template catalog.

Scope: credential bundles remain a separate fallback for subscription/OAuth logins that cannot accept an API key. They are not involved in the OpenCode + Z.AI path above.

Sandbox boot sequence

  1. Validate the requested harness, provider, and model against the server-side template catalog.
  2. Accept the API key as a write-only request field and create a short-lived encrypted pending-secret record.
  3. Select the immutable harness + provider NodeOps root filesystem.
  4. Create the sandbox and start the signed AO worker.
  5. Worker exchanges its short-lived bootstrap identity for the pending key, scoped to session + worker epoch + template.
  6. Delete or invalidate the pending-secret record immediately after successful redemption.
  7. Start the agent child process with the key in the one allowlisted environment variable.
  8. Run the template’s provider/model probe with a short timeout.
  9. Start the turn only after the probe reports authenticated.
  10. On shutdown, zero transient buffers and remove the sandbox with its ephemeral volume.

Security requirements

Storage

  • Envelope encryption with environment-specific KMS keys.
  • Separate record per organization, user, harness, and provider account.
  • No credentials in container images, ConfigMaps, Git, logs, analytics, or command arguments.

Delivery

  • Short-lived single-use lease bound to the current worker epoch.
  • Worker-only mTLS or signed-JWT endpoint.
  • Allowlisted paths and environment names per harness.

Execution

  • Non-root UID 10001 and owner-only modes.
  • Read-only application image and non-secret provider config.
  • Initial mode: API key exists only in worker and agent-process memory for an ephemeral session.
  • Hardened mode: an AO-owned loopback credential proxy holds the upstream key and injects the provider authorization header.
  • OAuth-only templates use a separate writable credential store and one active refresher.
Never accept an arbitrary archive and extract it into the worker home. The driver must reject absolute paths, .., symlinks, devices, sockets, unexpected filenames, oversized files, and modes broader than owner-only.

Credential refresh concurrency

OAuth providers may rotate refresh tokens. AO must grant an exclusive account lease before starting a sandbox that can refresh a shared credential. A successful update increments credential_generation; stale workers cannot overwrite a newer generation.

UPDATE agent_credentials
SET encrypted_payload = :payload,
    generation = generation + 1,
    updated_at = now()
WHERE id = :credential_id
  AND generation = :expected_generation
  AND active_lease_epoch = :worker_epoch;

Rollout plan

Phase 1 — prove the template flow

  1. Build and pin the opencode-zai Linux template.
  2. Add the write-only API-key field and request-body redaction.
  3. Add one-time post-boot key delivery to the signed worker.
  4. Inject ZAI_API_KEY only into the OpenCode child process.
  5. Validate the configured provider and model before the first turn.

Phase 2 — API-key templates

  1. Add reviewed harness + provider combinations to the template catalog.
  2. Pin every harness version, provider ID, default model, and secret environment mapping.
  3. Add Claude, Cursor, Aider, Droid, Crush, Qwen, Continue, Goose, Vibe, Devin, Kiro, and Autohand where an API key is supported.

Phase 3 — OAuth and native auth

  1. Add Claude setup tokens, Codex token import, and officially supported device-login flows.
  2. Add portable bundles for Kimi, Cline, Amp, Grok, Pi, Kilo, Kimchi, Prime, Muse, and OMP only where required.
  3. Prefer workload identity for Bedrock, Vertex, and Azure.
  4. Add refresh-generation synchronization for rotating OAuth credentials.

Phase 4 — unresolved interactive flows

  1. Evaluate AGY and any remaining keyring-only login.
  2. Add a user-mediated device-code relay only when officially supported.
  3. Keep unsupported harnesses visibly login_required.

Acceptance tests

  • Clean Debian sandboxes created with the OpenCode, Pi, and OMP Z.AI templates can each complete a real provider probe.
  • Changing only the supplied key requires no image rebuild or config rewrite.
  • An unsupported harness/provider/model combination is rejected before a sandbox is created.
  • The API key is absent from the pod definition, NodeOps template, image layers, config files, process arguments, responses, error envelopes, logs, audit rows, crash reports, and telemetry.
  • The pending API key can be redeemed only once and only by the assigned worker epoch.
  • An expired pending key cannot start the agent.
  • An expired OAuth access token refreshes once and persists a higher credential generation.
  • Two workers cannot concurrently refresh the same account credential.
  • A revoked token transitions the session to login_required without deleting workspace data.
  • A mismatched harness or account cannot redeem another credential lease.
  • Destroying a sandbox removes all decrypted credential files.
  • Every image declares and verifies its exact harness version at build time.
  • AMD64 and ARM64 templates are tested separately wherever both are advertised.

Non-goals

  • Extracting credentials from macOS Keychain, Windows Credential Manager, or browser storage.
  • Sharing one personal subscription credential across unrelated AO users.
  • Reverse-engineering undocumented token formats.
  • Allowing credentials to select or alter the sandbox provider.
  • Claiming a harness is Cloud-ready merely because AO can locate a local credential file.
